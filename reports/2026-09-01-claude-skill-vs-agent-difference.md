# What Is the Difference Between an AI Skill and an AI Agent?

**Question:** What is the difference between an AI skill and an AI agent? (Scoped by Rick to the Claude/Anthropic ecosystem specifically — Claude Code's Skill tool vs. Agent tool/subagents vs. the Claude Agent SDK — not a general industry survey.)

## Bradlee's Synthesis

Rick asked for the Claude/Anthropic-specific difference between a Skill and an Agent. The short answer: **a Skill is a capability; an Agent is the runner that decides whether to use it.**

Mechanically, per Anthropic's own current documentation (Sherlock, fetched fresh 2026-09-01): a Skill is a folder with a `SKILL.md` file that loads via progressive disclosure — description always in context (~100 tokens), full instructions loaded only when triggered (under 5k tokens), bundled resources loaded only when referenced. It runs inside whatever session invoked it, sharing that session's context window and, by default, its tools. It has no isolation of its own and no ability to decide, on its own, to run.

An "Agent" names the loop that decides what to do next: evaluate the current state, call a tool (maybe a Skill, maybe something else), receive the result, repeat until there's nothing left to call, then return. Anthropic's own Agent SDK definition puts it plainly: "an application that completes a task by planning its own steps and calling tools." That loop shows up at three depths in the Claude ecosystem, and this is worth stating explicitly since it's the part most likely to cause confusion: (1) the whole Claude Code session itself is running that loop; (2) a **subagent**, spawned via the Agent tool, is a fresh instance of the identical loop — isolated context, restricted tools, returns only a summary; (3) the **Agent SDK** packages that same loop as a Python/TypeScript library so it can run inside someone else's application, entirely outside Claude Code's terminal.

Euclid's framing — capability vs. runner — holds up under Popper's pressure, with one honest concession Seldon flagged rather than smoothed over: a sufficiently elaborate Skill (this very report, built by the `nexus` Skill, is the example) can produce behavior that looks indistinguishable from an autonomous agent run to the person watching it. The mechanism-level distinction is real — no new context window, no tool restriction, no summary-only return happened anywhere in this report's production — but it isn't always visible from the outside. That's a real limit on the claim, not a flaw in the analysis, and it's worth remembering the next time "just a Skill" sounds like it should mean "simple."

The most concrete finding for Rick personally: this report is a live case of the terminology collision Popper surfaced. The Nexus's nine "agents" — Sherlock, Euclid, Popper, and the rest — are role-framings this one Skill invocation applies in sequence, not Claude Code's technical subagent primitive; no isolated context window was ever created for any of them in this run. Both usages of "agent" are legitimate English, but they're not the same referent, and `Nexus Workflow.md` currently doesn't disambiguate between them anywhere. That's a documentation gap worth a one-line fix — flagged here for Rick's call, not actioned unilaterally, since it falls outside this report's scope.

Seldon's two forecasts both point the same direction: the Skill and Subagent primitives are converging (about 6 months to 3 years out, median 14 months) and Skills specifically gaining subagent-like tool-restriction/trust controls (about 1 to 2.5 years out, median 18 months) — both reasoned judgment from the pace of the last year's shipped features (the `skills` preload field, `context: fork`, `skillOverrides`, Enterprise content scanning), not measured data.

## Sherlock: What Are the Facts?

Three official, currently-live sources establish the facts (each re-fetched during this engagement rather than assumed current from the August report):

**Skills** (`platform.claude.com/docs/en/agents-and-tools/agent-skills/overview`, re-fetched 2026-09-01): A Skill is a directory containing a required `SKILL.md` (YAML frontmatter: `name`, `description`; body: instructions) plus optional bundled files. It loads via **progressive disclosure** — three levels: metadata (always loaded, ~100 tokens), instructions (loaded only when the description matches the current request, under 5k tokens recommended), and resources/scripts (loaded only when referenced, zero cost until accessed). Crucially: a Skill **runs inside the invoking session's own context window**, using that session's own tools (filtered only if `disallowedTools` is set) — it has no isolation boundary of its own. Security guidance is unchanged from the August report: use Skills only from yourself or Anthropic; a Skill is an instruction set that can direct bash/network/filesystem actions, and the format itself enforces no sandboxing in Claude Code specifically (full network access, same machine access as anything else you run).

**Subagents / the Agent tool** (`code.claude.com/docs/en/sub-agents`, fetched fresh this engagement): A subagent is "a specialized AI assistant that handles specific tasks in its own isolated context window." Defined the same way as a Skill mechanically (YAML frontmatter + markdown body, `name`/`description` required), but invoked through the **Agent tool**, and structurally different in three ways the docs state explicitly:
- **Isolation:** fresh, isolated context by default (no conversation history, no output style, no already-invoked skills) — versus a Skill's shared context. The one exception is a **fork** (`/subtask`), which inherits the full parent conversation instead of starting fresh.
- **Tool access:** filtered by an allowlist/denylist (`tools`, `disallowedTools`) and, for background subagents, a second stricter filter — versus a Skill's default of inheriting the full session's tools.
- **Output:** returns only a summary to the parent; exploration, logs, and file contents stay isolated — versus a Skill's output appearing inline in the same conversation.

The docs' own comparison table makes this the canonical answer to the literal question asked:

| Feature | Subagent | Skill |
|---|---|---|
| Isolation | Own context window | Runs in main conversation's context |
| System Prompt | Custom per subagent | Snippet injected into main prompt |
| Tool Access | Restricted per definition | Same as main conversation (unless restricted) |
| Output | Summary returned | Inline in conversation |
| Best For | High-volume operations, parallel work, enforced constraints | Reusable prompts/workflows within main context |

A subagent can have Skills **preloaded** into it via a `skills` frontmatter field — so the two primitives compose (an agent can consume a skill) rather than sitting as pure alternatives. Subagents can spawn further subagents up to 3 layers deep by default, run up to 20 concurrently, and Claude Code ships several built-in ones (`Explore`, `Plan`, `general-purpose`, plus this project's own `claude-code-guide` and `statusline-setup`).

**The Claude Agent SDK** (`code.claude.com/docs/en/agent-sdk/overview` and `.../agent-sdk/agent-loop`, fetched fresh): Anthropic's own definition, stated plainly: *"An agent is an application that completes a task by planning its own steps and calling tools that read files, run commands, or edit code."* The SDK is a Python/TypeScript library that exposes **the same agent loop that powers Claude Code** — receive prompt → evaluate and (maybe) call tools → execute tools → repeat until a response has no tool calls → return result — as a programmable primitive outside the terminal. This is the third, broader sense of "agent" in the Claude ecosystem: not a spawned sub-unit inside a session, but the loop mechanism itself, wrapped as something you can embed in your own application. The SDK's own capability table lists "Subagents" (spawn specialized agents for focused subtasks) as *one capability available to* an SDK-built agent — alongside Skills, hooks, MCP, permissions, and sessions — confirming subagents are a sub-primitive nested inside the broader SDK sense of "agent," not a competing definition.

## Euclid: What Must Be Fundamentally True

Strip away product naming and three things hold regardless of which specific primitive (Skill, subagent, or SDK-level agent) is being discussed:

**A Skill is conditionally-loaded context; it is not itself a locus of execution.** Its entire mechanism is *when* content enters an already-running context window, not *what* does the running. A Skill cannot decide to run itself, cannot choose not to finish, cannot hold its own state independent of the session that invoked it. It is closer to a reference the current reasoning process consults than to a thing that acts.

**An "agent," in every sense used across these three sources, names a loop that plans and acts — the thing doing the consulting, not the thing consulted.** The SDK's definition is the cleanest statement of this: something that *plans its own steps* and *calls tools*, repeatedly, until it decides it's done. A subagent is one concrete, isolated instantiation of that loop, spun up for a bounded task and reporting back a summary. The SDK's "agent" is the same loop, offered as a library primitive so it can run outside Claude Code's terminal UI, in someone else's application. All three "agent" usages point at the identical mechanism — evaluate, act, evaluate again — at different scopes: the whole session, an isolated sub-unit of it, or a program built from it.

**The two categories are not parallel alternatives — they compose, and the composition is the actual architecture.** A Skill is something an agent (in any of the three senses) *reads and follows*; it changes what the loop does on its next few turns, but the loop itself — the thing deciding whether to read the Skill at all, whether to call a tool, when to stop — is always the agent, never the Skill. This is why a subagent can have Skills preloaded into it (`skills:` field) but a Skill cannot "contain" a subagent the same way: a Skill's instructions can *direct* the current agent to invoke the Agent tool and spawn one, but the Skill itself never becomes the isolated execution unit; it stays a passage of text the loop is following.

Put plainly: **a Skill is a capability; an agent is a runner.** The runner decides which capabilities to load, when, and what to do with their output. Nothing about Skills changes the runner's job; nothing about being a runner requires consulting any given Skill. That asymmetry — one is passive, filesystem-resident, and inert until read; the other is the active process doing the reading — is the fundamental distinction underneath every mechanical difference Sherlock documented above.

One immediate implication, worth stating before Popper's stage: **this very report is generated by a Skill (`nexus`) directing an agent (this Claude Code session) through an eleven-stage instruction sequence** — and nowhere in that sequence does a new isolated context window, a restricted tool set, or a summary-only return get created. Every "agent" named in this report so far (Sherlock, Ryan, Euclid) is a role-framing the *same* loop adopted in sequence, not a technical subagent. That is exactly the terminology collision the harness-architecture report flagged in July, and it is about to become Popper's main objection.

### A Worked Example: The Nexus System

Tufte's diagram later in this report closes on a single sentence worth anchoring an example to right now, since Nexus is a live instance of it, clause for clause: *"A Skill is a capability the loop reads. An Agent is the loop itself — the thing deciding what to read, when, and whether to spawn another instance of itself."*

- **The capability the loop reads:** `.claude/skills/nexus/SKILL.md` — one Skill, triggered when Rick types `/nexus` or asks a Nexus-shaped question. Its body is the eleven-stage sequence (Bradlee's pre-flight, Alexandria's opening, Sherlock, Ryan, Euclid, Popper, Seldon, Tufte, Turing, Bradlee's synthesis, Alexandria's close) this very report is following right now. Every "then Agent X..." line in `Nexus Workflow.md` is a paragraph inside that one file — not a separate program, not a separate install.
- **The loop itself:** this Claude Code session — the one continuous process that read the Skill's description, matched it against Rick's request, loaded its body, and has been deciding ever since, turn by turn, what to do next: call `WebFetch` for Anthropic's docs, call `Bash` to search prior reports, invoke the `epic-infographics` skill for Tufte's diagram, call `Bash` again to publish via git. Nothing about "being Sherlock" or "being Popper" changed *which process* was running; it changed which passage of the one loaded Skill body the loop was currently following.
- **"Whether to spawn another instance of itself":** this is the one branch Nexus's design deliberately doesn't take. The loop could, at any stage, have called the Agent tool and spawned a real subagent — Sherlock as an isolated, `WebFetch`/`WebSearch`-restricted subagent reporting back only a summary, say. `Nexus Workflow.md` doesn't ask for that, and this run didn't do it: every stage's full output — not a summary of it — sits in this one report and in this one session's context. That is a deliberate architectural choice, traceable to `reports/2026-07-20-nexus-harness-architecture.md` (which found the same thing before Ryan or Bradlee even joined the chain), not an oversight — and it's exactly why Popper's counterexample below lands as hard as it does: nothing about the loop's *shape* changed across all eleven stages, only what it was reading.

Seen this way, "nine Nexus agents" is nine passages of one Skill, read by one loop, in sequence — not nine loops. If Nexus were ever rebuilt so each stage ran as an actual Agent-tool subagent, the quoted sentence above would still hold; it would just describe nine new loop instances instead of one loop reading nine passages. That rebuild hasn't happened. The terminology collision Popper raises next is a collision about the *word* "agent" as Nexus currently uses it — not, yet, evidence of a collision in the underlying architecture.

## Popper: Where Euclid's Clean Distinction Gets Harder

Euclid's "capability vs. runner" framing is accurate, but it understates three places where the boundary is fuzzier than the account above makes it sound, and a fourth place where the account is actively self-undermining given what this very report is doing.

**First — a subagent's system prompt is itself just instructions, structurally not that different from a Skill's body.** Both are markdown text with YAML frontmatter (`name`, `description` required in both cases) that shapes what Claude does next. If the only real difference is *isolation* (own context window, restricted tools, summary-only output) rather than anything about the *content*, is "Skill vs. Agent" actually a difference in kind — or is a subagent just "a Skill that additionally gets its own context window and a narrower toolset"? Euclid's runner/capability framing glosses over how mechanically similar the two definitions are at the file level.

**Second — the Agent SDK's own documentation lists Subagents as a capability *of* an agent, the identical relationship a Skill has to an agent.** If "spawn subagents" and "invoke skills" sit side by side in the same capability table as things an SDK-built agent can do, why does one of those capabilities (subagents) count as "another agent" in Euclid's ontology while the other (skills) counts as "not an agent at all"? The recursion needs to be justified, not asserted.

**Third, and most concrete — this report is a live counterexample to "a Skill cannot itself be a locus of execution."** The `nexus` Skill's instructions produced eleven stages of autonomous, multi-step, tool-calling behavior — web fetches, file reads, a diagram build, a GitHub publish — indistinguishable in effect from what an agent does. Euclid's own closing paragraph tries to have it both ways: it says the Skill "directs" the agent to act, but from Rick's vantage point as the person who typed `/nexus`, what he set in motion functionally *is* an autonomous multi-step agent run. If the observable behavior is the same, in what sense is the underlying distinction not just an implementation detail invisible to the person using it?

**Fourth — the terminology collision Euclid flagged (Nexus's nine "agents" are role-framings, not subagents) is not a minor footnote; it means Rick's own project has been using "agent" in a way that contradicts the technical definition this very report is establishing, for two months, across dozens of published reports, without anyone flagging it until now.** That's either a genuine problem worth fixing in `Nexus Workflow.md`, or evidence that the "everyday" sense of "agent" (a persona with a job) is doing legitimate work that the technical definition doesn't capture and shouldn't be expected to override.

## Seldon: Resolving Popper's Objections, and What's Next

Taking each in turn:

**On subagents being "just a Skill with isolation bolted on":** resolved, not dismissed — Popper is right that the file format is nearly identical, but the isolation *is* the substantive difference, not a cosmetic add-on, because of what it structurally enables rather than what it superficially looks like. A Skill sharing the invoking session's context cannot run concurrently with that session's other work, cannot be given a genuinely narrower permission scope without changing the whole session's rules, and cannot be interrupted or resumed as an independent unit (Claude Code's subagent transcripts persist independently and can be resumed via `SendMessage` — a Skill has no equivalent identity to resume). Those are different affordances, not just a different label on the same thing. So: same file shape, genuinely different capability class, because isolation is a property of the *execution*, not the *text*.

**On the SDK listing subagents as a capability the same way it lists skills:** resolved by pointing out this isn't actually symmetric once you look past the table formatting — it's recursion, not category confusion. An SDK-built agent's "subagents" capability means it can spawn *another instance of the identical loop mechanism it itself is*, scoped narrower. Its "skills" capability means it can load *conditional text* that changes what the one loop already running does. A function that can call itself recursively and a function that can read a config file are both listed as "things the function can do," but they're not the same kind of thing — one produces a new instance of the mechanism, the other feeds the existing instance more input. The table's flat listing is a presentation choice, not evidence the underlying primitives are equivalent.

**On this report itself being a counterexample:** this is the one place Seldon does *not* fully resolve Popper's objection — it stands, with a clarification rather than a rebuttal. Popper is correct that from the outside, "Rick typed `/nexus` and eleven stages of autonomous tool-use happened" is functionally indistinguishable from "Rick started an agent." The distinction Euclid drew survives on mechanism (no new context window was created, no tool restriction was applied, no summary-only return happened — this whole report sits in one continuous session transcript) but Popper is right that it does *not* survive on observable behavior, and the report should say so plainly rather than paper over it: **a sufficiently elaborate Skill can make the mechanism-level distinction invisible to the person using it, even though the distinction remains real underneath.** That's a legitimate limit on how far "Skill = passive capability" can be pushed as a claim about what a Skill can *look like* in use, separate from what it structurally *is*.

**On the terminology collision in Nexus's own workflow:** resolved as "not a bug, but worth naming" — both readings Popper offered are correct simultaneously. "Agent" as Nexus uses it (a persona with a distinct guiding question, applied within one Skill invocation) and "agent" as Claude Code's technical primitive (an isolated, tool-restricted loop instance) are both legitimate uses of an overloaded English word for "something that acts with a purpose," and neither needs to yield to the other — but conflating them in conversation risks real confusion, e.g., "how many agents does Nexus run" has a different true answer depending on which sense is meant (nine role-framings vs. zero technical subagents, in the ad-hoc chain as currently implemented). This report's own existence is the evidence for recommending a one-line disambiguating note in `Nexus Workflow.md` — flagged for Rick's consideration, not actioned unilaterally, since it's a documentation change outside this report's scope.

**Forward-looking, in plain language rather than point estimates:**

- *How long before Claude Code's Skill and Subagent primitives converge further, functionally or in tooling* (e.g., a lightweight opt-in isolation mode for Skills, or subagents becoming cheap enough to replace most Skill invocations): the range runs from about 6 months to 3 years, with a median around 14 months. The low end is driven by the pace already visible in the last year — the `skills` field for preloading into subagents, `context: fork` for full-inheritance subagents, `skillOverrides` — which shows Anthropic actively iterating on exactly this boundary. The high end reflects that the current separation (shared-context/full-trust Skills vs. isolated/restricted Subagents) maps onto a deliberate security boundary, not just an oversight, and collapsing it further has real trust-model consequences Anthropic may choose not to take on quickly. This is reasoned judgment from the shipped feature history reviewed above, not measured data.
- *How soon Skills gain something closer to a subagent's tool-restriction model* (closing the trust gap the August report's Popper stage flagged — a Skill today inherits full session tool access by default): the range runs from about 1 to 2.5 years, with a median around 18 months, tracking the same convergence pressure as above but gated more by the security-review cost of getting a permission model right than by engineering effort. Driven off the same evidence: Enterprise-only content scanning today, no equivalent for individual/API-uploaded Skills — closing that gap plausibly comes bundled with any broader Skill/Subagent convergence rather than shipping first on its own.

Both ranges are Seldon's judgment based on the pace of the last year of Skills- and Subagent-related product changes documented in the sources below, not measured data — Rick should weight them as such.
