# Nexus External Recon (Passive OSINT)

A repeatable Sherlock-stage technique for building a real, non-fabricated external-exposure picture of a named company using only free, passive, legally-unambiguous sources — no paid subscriptions (Shodan, SecurityScorecard, BitSight, HaveIBeenPwned domain-verified search), no active scanning (no nmap/port scans, no login attempts, no directory brute-forcing), no dark-web/Tor access. Everything here is either information the target's own DNS/TLS infrastructure publishes by design, or a free public API.

**Ethical/scope boundary, non-negotiable:** passive only. The moment a check would require exploiting something, brute-forcing a path, logging into a portal, or browsing a criminal marketplace, stop and recommend the human run that step themselves with proper authorization — don't do it inside this skill.

## Before running

If the report will be published to a public repo (the default for `raceBannon99/The-Nexus`), that's a real decision, not a formality — publishing a real company's aggregated attack-surface findings publicly hands the same roadmap to any attacker who finds the report, even though every individual data point was already public. Surface this explicitly as a Bradlee pre-flight clarifying question (per the `nexus` skill) before doing any of the below — don't assume the default publish-to-main behavior is right for this kind of report. Get an explicit answer and log it.

## The checks, in order

1. **Confirm identity.** Web-search the company name to confirm the real domain and business context (what they do, who their clients/partners are) before touching any infrastructure — don't guess a domain from the name alone.
2. **DNS & WHOIS** (`dig`, `whois`) — A/AAAA, MX, NS, TXT records for the root domain; WHOIS for registrar, creation/update dates, DNSSEC status. TXT records are a goldmine: third-party SaaS domain-verification strings (Adobe, Atlassian, Cisco, Google, OpenAI, Anthropic, etc.) reveal the org's actual SaaS footprint, and SPF records reveal approved mail senders (often naming partner domains and specific sending IPs).
3. **HTTP headers** (`curl -sSI`) on the root domain and any `www`/app subdomain — reveals the hosting/edge stack (CDN vendor via `server`/`cf-ray` etc.), and the security-header posture (CSP, HSTS, X-Frame-Options, X-Content-Type-Options). Compare posture *across* properties on the same company — inconsistency between a marketing site and an internal tool is itself a finding.
4. **Certificate transparency** — the highest-signal free step. `crt.sh` is the best-known source but frequently times out under load; **use `https://api.certspotter.com/v1/issuances?domain=<domain>&include_subdomains=true&expand=dns_names` as the primary source**, it's reliably fast. Extract every unique `dns_names` entry across all returned certs — this surfaces subdomains the company never intended to be discoverable (client-named integration endpoints, dev/qa/stg/sandbox environments, VPN gateway hostnames) because CA/Browser Forum rules make certificate issuance permanently, publicly logged regardless of whether the service is ever exposed to the internet. **Wildcard certs (`*.foo.com`) mean the true subdomain count is always higher than what's enumerable this way — say so explicitly, never present the CT-log list as exhaustive.**
5. **Resolve and lightly probe the interesting subdomains** found in step 4 — `dig +short A` to see if each still resolves (a cert existing for a hostname that no longer resolves is itself worth noting: the *existence* of e.g. a VPN gateway leaked permanently via CT logs even if it's not live now), then one passive `curl -sSI` per genuinely interesting host to see status code and stack. Do not go further than a root-path HEAD/GET — no path enumeration, no parameter fuzzing.
6. **TLS certificate spot-check** (`openssl s_client ... | openssl x509 -noout -issuer -dates`) on a couple of the found hosts — confirms cert issuer/validity, catches obviously expired or self-signed certs.
7. **Public breach-corpus check** — HaveIBeenPwned publishes its full list of named breaches at `https://haveibeenpwned.com/api/v3/breaches` with no auth required; check whether the target domain/company itself appears as a breach *source*. **This is fundamentally different from, and much weaker than, checking whether the company's employee emails appear as breach *victims*** — that requires HIBP's domain-verified search (proof of domain ownership) or a specific email address. Never conflate the two in the writeup; "not a breach source in HIBP's public list" is not "no employee credentials have leaked."
8. **Public GitHub search** (`api.github.com/search/repositories?q=<company>`) — repo search needs no auth; code search does. Note the existence of company-affiliated accounts/repos as a category of exposure (potential secrets, org-chart/employee enumeration via username patterns) but **do not** name individual employees found this way in a report that will be published, and do not run a secrets-scan against their code yourself — flag it as the next authorized step for the company's own team.
9. **Web search for prior incidents** — company name + "breach"/"leaked"/"hacked"/"CVE"/"vulnerability", plus a check of relevant vendor CVE databases if the company's product name could collide with an unrelated product (it often will).

## What this cannot answer — say so explicitly every time

- Dark-web marketplaces, criminal forums, stealer-log aggregators, and "access-for-sale" listings require dedicated commercial monitoring (Flare, Recorded Future, Intel 471, KELA, SpyCloud, Constella) or Tor access this skill does not have and should not attempt. Absence of a finding here is a coverage gap, not a clean bill of health.
- Active scanning (Shodan-grade port/service enumeration, vulnerability scanning) is out of scope; passive DNS/cert data tells you *where* to point an authorized scanner, not what's actually vulnerable.
- Asset-attribution confidence should be stated explicitly and gradiently, not asserted as binary: a subdomain under the target's own DNS zone is high-confidence theirs regardless of what shared-cloud IP sits behind it (owning the DNS record is the attribution signal, not the IP); a bare IP or a mention in a general web search is much weaker and should be labeled as such.

## Output shape

Feed findings into the normal Sherlock → Euclid → Popper → Seldon → Tufte sequence. Popper should always challenge attribution-confidence claims and any "not found" framing; Seldon should resolve those explicitly rather than let a passive-recon report read as more conclusive than it is. A layered "external exposure map" (DNS/registrar → edge/CDN → hosting platforms → named client-integration surface → remote-access/VPN) is usually the right Tufte diagram — a table alone won't carry the layering.
